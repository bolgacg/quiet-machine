An interactive public study · observability for machines in the field

How do you catch a machine that fails without an error?

Five production incidents from an estate I run had one thing in common: nothing ever turned red. A recorder wrote empty files for twenty hours, a service was refused 48,752 times, and every dashboard stayed green, because the checks measured presence when they should have measured progress. This page lets you inject those five failure classes into a simulated sorting line and watch two monitors race to notice; then it shows the real kit, with its measured proof run.

Section 1 · What you need to know

Five things, then the page makes sense

  1. Telemetry is the stream of numbers a machine reports about itself: items processed, last successful action, queue depth. Monitoring is deciding, from that stream, when to wake a human.
  2. The oldest trap in monitoring is presence versus progress: "the process is running and its heartbeat arrives" is presence; "the work counter advanced in the last minute" is progress. A machine can heartbeat forever while doing nothing.
  3. An alert rule is a written condition evaluated continuously ("no successful fetch for 60 seconds"). In this kit every rule lives in git, names its runbook, and carries a unit test that proves it fires on its incident's shape and stays silent on a healthy one.
  4. The stack is the standard open one, each piece one sentence: NATS is the message bus the telemetry travels on; the OpenTelemetry Collector translates it into metrics; Prometheus stores the metrics and evaluates the rules; Alertmanager delivers what fires; Grafana draws it.
  5. The simulator below is a cartoon built for this page: a laundry-style sorting line with compressed time, so failures become visible in seconds. The measured numbers from the real kit follow it, clearly separated.
Heartbeat
a periodic "I am alive" signal. Proves the process runs; proves nothing about work.
Presence monitor
the naive check used as the baseline here: green while the process is up and heartbeats arrive within 90 seconds.
Progress rules
the kit's approach: every station must show advancing work, matching identity, and admitted throughput; each rule fires on the absence of one of those.
Time to detect
seconds from fault injection to the first firing alert. The simulator counts it live; the real kit's proof script measured it.
Runbook
the page a responder opens when an alert fires: what it means, what to check first, how it was tested.

Act 2 · The real kit

The same idea, built and measured

quiet-machine is the working version of act 1: two collector services that behave like machines at a customer site, telemetry as OpenTelemetry over NATS JetStream, a bridge that verifies each message's claimed identity against the subject it arrived on, an OpenTelemetry Collector into Prometheus, eight alert rules with promtool unit tests, and an Alertmanager route that writes every notification to a ledger. A fault injector can trigger each incident on purpose, and a proof script measures what happens.

The eight rules, one line each

QuietMachine · heartbeat age over 60 s: the machine stopped reporting.
SilentWriter · files advance without data frames: incident 1's guard.
HungPoller · one leg's last success goes stale while the process lives: incident 4.
SilentRefusals · the admission gate refuses while status stays green: incident 5.
IdentityMismatch · a message claims a name that does not match its channel: incident 3.
PressureStall · CPU pressure over 20: read pressure before blaming the network, incident 2.
CollectorMissing · a machine that should report has no series at all.
BusSilent · the bridge itself stops forwarding: the watcher is watched.
The rules are the product; everything else is plumbing. Each of the eight names the incident it guards against and the runbook a responder opens, and each carries a unit test that proves it fires on its incident's series shape and stays silent on a healthy board. The stack around them is deliberately standard, so the same rules would carry to any Prometheus estate.
What this page gets wrong, stated first

Limits and misses

  • The simulator is a cartoon. Time is compressed tenfold, rates are invented, and the presence monitor is deliberately the weakest defensible baseline (process up plus heartbeat). A tuned liveness check with rate thresholds would catch some of these; the simulator argues the design point, not a benchmark.
  • The proof run is one run on one host. Bare binaries on a 4-core machine, 29 August 2026. Latencies will differ elsewhere; what carries is that every alert fired, resolved and delivered, and that the script to re-measure ships with the kit.
  • The Docker path is verified only in CI. The compose file passes the end-to-end job on GitHub Actions; it has never been run on my machines, which have no Docker.
  • PressureStall is informational. Its threshold is host-dependent and it deliberately does not resolve-notify; it is a diagnosis aid, not a page-me alert.
  • No claim of scale. Two simulated collectors, one bus, one Prometheus. Fleet cardinality, retention and federation are real problems this kit does not touch.
Coda · Where this comes from, and how to run it

Method and sources

Origin. The five failure classes are five real incidents from the production estate I have run since 2024, written up in the note "The quiet machine" that accompanies my Site Reliability Engineer application. Every alert in the kit is one incident's guard, generalised.

Run it. git clone github.com/bolgacg/quiet-machine, then ./run-local.sh fetch && ./run-local.sh up on bare binaries, no Docker needed. tools/fault.py injects any incident; tools/prove.py re-measures the proof table.

This page. The simulator is docs/app.js, plain JavaScript, no libraries; the proof table is copied verbatim from the repository and says so where it appears.

Simulator numbers are computed live in your browser; the proof table is quoted verbatim from proof/RESULTS.md in the repository. Bolgaç Gülen, September 2026.
